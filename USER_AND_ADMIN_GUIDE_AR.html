دليل المستخدم والمشرف — ALP Manager v1.0.0

بالعربية (RTL) · يشمل التثبيت، الاستخدام اليومي، إنشاء السياسات، التطبيق والتحقق، الاسترداد، الجرد، التشخيص، واستكشاف الأعطال

1) التثبيت

  • نسخة المثبّت: شغّل AndroidLockdownManager_Setup-v1.0.0.exe — تثبيت لكل مستخدم (بلا صلاحيات إدارة)، إنشاء اختصارات قائمة ابدأ + سطح المكتب، وسجل إزالة مستقل. الإزالة من «الإعدادات ← التطبيقات ← ALP Manager ← إلغاء التثبيت» أو ... --uninstall.
  • النسخة المحمولة: شغّل AndroidLockdownManager-v1.0.0-windows-x64-portable.exe مباشرة.
  • تحقق من بصمة الملف: Get-FileHash .\AndroidLockdownManager_Setup-v1.0.0.exe -Algorithm SHA256 مقابل RELEASE/SHA256SUMS.txt.
  • البيانات تُحفظ خارج الحزمة في %LOCALAPPDATA%\ALPManager\ (قاعدة البيانات، مفاتيح DPAPI، سجلات، تقارير) — لا تتأثر بإعادة تثبيت النسخة المحمولة.

2) أول تشغيل

  1. التطبيق يفتح مباشرةً بوضع «المشغّل المحلي» (لا تسجيل دخول).
  2. صفحة «الأجهزة» تُظهر حافلة ADB حيّة (تحديث كل 4 ثوانٍ): الأجهزة المكتشفة جاهزة/غير جاهزة (فعّل «تصحيح أخطاء USB» على الهاتف وأكّد الإذن).
  3. اضغط «تسجيل الجهاز» — يُنشأ device_id تلقائيًا (لا يُكتَب يدويًا)، ويُصدر تلقائيًا بيان استرداد خاص بالجهاز لهذه الوحدة (مشفّر DPAPI).
  4. اختر «فتح الجهاز (تحديد)»؛ يُحفَظ سياق الجهاز النشط ويعود بعد إعادة التشغيل.

3) السياسات

سياسات جاهزة: هاتف فقط · القياسية · إغلاق كامل · تقليص جزئي · صيانة · عزل.
سياسة مخصصة: في صفحة السياسات، سمِّ السياسة واختر الفئة (6 فئات: عامة/تقييد/اتصالات/…) والخطورة، وحدِّد الأجنحة (27 ميزة قابلة للقفل) من الشبكة، ثم «إنشاء» → تُخزَّن بمعرّف POL-CUST-* وتظهر في قائمة التطبيق مباشرةً.
إغلاق كامل بمعالج: زر المعالج يفتح نافذة 25 ميزة محدّدة مسبقًا (اسم اختياري) → سياسة FULL_LOCKDOWN/CRITICAL.

4) التطبيق والتحقق

  1. اختر الجهاز النشط والسياسة → «تطبيق مع المعاينة»: المعاينة تعرض المتطلّبات مقابل الحالة الحالية على الجهاز (source: REAL_DEVICE | DEVICE_NOT_ATTACHED).
  2. يعمل فحص مسبق (preflight): التسجيل، معرفة السياسة، اتصال ADB، قابلية قراءة قيود الجهاز، قناة Device-Owner، حيازة البيان، النطاق — PASS/CONDITIONAL/FAIL.
  3. طلب العملية الحساسة يتطلب حيازة البيان: تظهر شاشة تأكيد تعرض معرّف الاسترداد (XXXX-XXXX) للجهاز المطلوب.
  4. أثناء التنفيذ تُقفل الأدوات؛ النتيجة تُعرض بجدول: الجهاز/السياسة/المرحلة/مصدر الدليل/الحكم/الالتزام/evidence_id/audit_id/سلامة السلسلة.
قراءة الحكم بصدق: «متوافق» تُعرض فقط بدليل حقيقي. «غير معروف» (UNKNOWN) تعني: لا يوجد دليل إثبات بعد (غالبًا قبل تثبيت مالك الجهاز) — لا يُفسَّر غياب الإثبات نجاحًا.

5) حالة الالتزام (compliance)

بعد كل تطبيق تُكتب لقطة التزام لكل جناح: «المتوقَّع مقابل الفعلي» (خريطة JSON في جدول compliance) مع checked_at. لوحة «حالة الالتزام» تعرض: متوافق / متوافق جزئيًا / غير متوافق / غير معروف / غير مدعوم.

6) الاسترداد (المشرف)

  • بيانات الاسترداد تُحفظ مشفَّرة (DPAPI، هذه الوحدة فقط)، تُعرض بصورة recovery_id فقط.
  • R1/R2 (إنعاش/استرداد) تتطلب تأكيدين باسْمَين مختلفَين + السبب؛ R3 (استعادة إعدادات المصنع عبر القنوات الحرجة) يُسجَّل REFUSED صادقًا ما لم تكن القناة مدعومة.
  • إصدار/تدوير/إلغاء: صفحة «الاسترداد» — الأزرار متاحة فقط مع حيازة البيان الخاص بالجهاز المعني.

7) التطبيقات (جرد صادق)

صفحة «التطبيقات» تعرض جرد الحزم الفعلي من الجهاز (pm list packages / -3): حزم الجهات الخارجية والنظام، مع بحث وفلاتر. المنصة توضح بشفافية أن حظر/إزالة التطبيقات يصبح ممكنًا فقط بعد Device Owner عبر وكيل DPC؛ العرض الحالي للقراءة فقط ولا يوحي بإمكانية غير متوفرة.

8) التشخيص والسجلات

  • صفحة «التشخيص»: قاعدة البيانات، ADB، الجلسة، سلامة سلسلة التدقيق، حالة التمهيد.
  • السجلات: %LOCALAPPDATA%\ALPManager\logs\alp.log (+ startup-error.log عند فشل الإقلاع).
  • نوافذ الأوامر لا تومض: كل أدوات adb/dumpsys/powershell تعمل مخفية.

9) استكشاف الأعطال
