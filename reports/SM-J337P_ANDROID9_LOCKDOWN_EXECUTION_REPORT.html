معلومة حرجة مثبتة مصدريًا (AOSP android-28): قائمة GLOBAL_SETTINGS_WHITELIST في DevicePolicyManagerService لإصدار API 28 لا تتضمن Settings.Global.WIFI_ON ولا BLUETOOTH_ON (نُقلتا إلى مجموعة GLOBAL_SETTINGS_DEPRECATED). أي أن إيقاف Wi-Fi/Bluetooth عبر setGlobalSetting من Device Owner على Android 9 سيرمي SecurityException. لذلك إطفاء الراديوهات يتم عبر تطبيق الوكيل نفسه (WifiManager.setWifiEnabled / BluetoothAdapter.disable) ثم تُمنع إعادة التشغيل عبر تقييدات DPM وكسب Knox.

1) الملخص التنفيذي — Executive Summary

يهدف هذا المشروع إلى تحويل Samsung Galaxy J3 Achieve (SM-J337P) الذي يعمل حاليًا بنظام Android 9 (Pie) / API 28 / One UI 1.1 مع Knox 3.3 (Knox API 28) و SEAndroid في وضع Enforcing إلى جهاز مؤسسي مخصص (Locked-Down Enterprise Phone) عبر برنامج إدارة سطح مكتب (Windows EXE) ووكيل Android يعمل كـ Device Owner (DPC)، مع آلية تحقق واستعادة كاملة. هذا مشروع Pilot على جهاز واحد كخطوة تمهيدية قبل التعميم. الهدف ليس ترقية النظام إلى Android 15، بل قياس القدرات الفعلية والحدود الحقيقية لـ Android 9 + Knox 3.3 على هذا الطراز بالتحديد.

النتائج الرئيسية (ملخص)

  • الكاميرا، المواقع، تثبيت التطبيقات، المصادر غير المعروفة، USB، ADB، المصنع: يمكن قفلها عبر Device Owner بالكامل DOCUMENTED.
  • Wi-Fi وBluetooth والمكالمات فقط والإيقاف الحقيقي للبيانات: القفل النهائي (Hard-Off + منع إعادة التشغيل) يعتمد على Knox (allowWiFi ،allowBluetooth ،setCellularData) DOCUMENTED ويحتاج اختبارًا عمليًا على هذه الوحدة تحديدًا INFERRED.
  • الميكروفون: لا توجد آلية DPM قياسية على API 28؛ المتاح Knox فقط (setMicrophoneState) DOCUMENTED، مع اختبار أثرها على المكالمات.
  • منع الوصول للإنترنت مع إبقاء المكالمات والرسائل القصيرة: ممكن تقنيًا (إيقاف البيانات الخلوية + Wi-Fi + hotspot + tethering + VPN) لأن المكالمات/SMS تسير عبر نطاق CS وليس IP — مع تحفظات (MMS يتعطل، وتجاوز Wi-Fi يحتاج طبقة Knox)، وهو هدف قابل للإنجاز تجريبيًا.
  • Factory Reset: يمكن تقييده من الإعدادات، لكن لا يمكن ضمان منعه عبر Recovery/Odin؛ تُدار عبر إعادة-provisioning يدوية من المدير + FRP.
  • إعادة تسجيل الجهاز بعد الـ reset: لن تُجري تلقائيًا (لا يوجد EMM سحابي في هذه المرحلة)؛ يحتاج خطوة مدير عبر الـ EXE.

8.2 المقارنة الثنائية: Android-only مقابل Knox vs غير قابل للضمان

قابل للتنفيذ عبر Android DPM (DO) فقطيحتاج Samsung Knoxلا يمكن ضمانه برمجيًا
قفل الكاميرا (setCameraDisabled)، منع تثبيت APK، منع Unknown Sources، USB File Transfer، منع Factory Reset من الإعدادات، قفل App Install، قفل Safe Boot، حفظ الصلاحيات، تعطيل الإعادة للعديد من الإعدادات، قفل Location sharing، قفل Accounts/Settings جزئيًا، إخفاء/تعليق تطبيقات الإيقاف الحقيقي + منع إعادة التشغيل لـ Wi-Fi، Bluetooth، Cellular Data، الميكروفون، كل الـ tethering، ADB/USB عميق، Screen Capture، تحديث OTA، منع «Scanning» منع Factory Reset عبر Recovery/Odin، منع إعادة تفليش الـ firmware، منع إزالة الجهاز من يد مادي، إيقاف المكالمات الإجبارية (Emergency)، ضمان عدم تجاوز من قبل OEM-specific UI
تضارب موثق — يُدار صراحة: لا يمكن ضمان موثقة تفعيل «allowWiFi» / «setCellularData» بسلوك واحد على كل Firmwares؛ سلوك Samsung قد يختلف بين الإصدارات، ولا نعد بنتيجة قبل اختبار T-matrix على الوحدة الحالية. أي نتيجة تُظهر تحفظات تُدرج كـ «PARTIALLY SUPPORTED» وتُوصف بالضبط. الادعاءات «UNBREAKABLE» ممنوعة في هذا التقرير.

21) Factory Reset — التحليل الخاص

  • ماذا يحدث للسياسة؟ بعد أي Bring Reset كامل يُمسح Device Owner (DO لا يعيش إلا مع بيانات النظام)؛ الجهاز يرجع للحالة المقت. DOCUMENTED
  • هل يمكن إعادته تلقائيًا؟ لا — لا توجد بنية EMM/بث في هذه المرحلة. إعادة التسجيل بيد المدير عبر الـ EXE (لقطة ما بعد-reset → DO ← سياسة).
  • الطريقة الرسمية للإعادة: Factory Reset موثق في المعمل فقط (§42) → إعادة provision عبر adb أو QR (بشرط بلا حسابات) → إعادة تطبيق.
  • منع الـ factory reset من الإعدادات: DISALLOW_FACTORY_RESET وDISALLOW_SAFE_BOOT DOCUMENTED.
  • خارج النطاق: Recovery-mode reset وإعادة تفليش عبر Odin لا يمكن منعها برمجيًا؛ تُحد بالاعتماد على عمليات الإصلاح الداخلية، وكلمة FRP على الجهاز الذي كان مسجلًا بحساب (إذا فُعلت).
  • ماذا يحتاج تدخل المدير؟ أي إعادة-تسجيل بعد reset؛ وأي إجراء على جهاز معرض لـ Odin.

30) الحدود المعروفة — Known Limitations

  • لا يمكن برمجيًا ضمان منع إعادة تفليش الـ firmware أو الـ factory reset عبر Recovery.
  • لا يوجد ميزة «منع مستخدم إعادة تشغيل Wi-Fi» من Android-basic — لا بد من Knox على طراز Samsung.
  • قفل البيانات مع إبقاء مكالمات/SMS: MMS يتعطل؛ سلوك المشغل (IMS/Wi-Fi Calling) خارج نطاق التحكم الكامل.
  • تثبيت الـ DO يتطلب حالة «بلا حسابات» أو إعادة احتيال (قيود FRP حسب الحساب).
  • الـ hardening النهائي (ADB/USB) يُغلق أيضًا قناة الإدارة الخاصة بنا — قيد تصميمي مقصود.
  • نتائج T-matrix المعلقة تُترك as-is حاليًا: SUPPORTED لنقاط AOSP، و VENDOR DEPENDENT مع اختبار إلزامي لكل ما يقع على طبقة Samsung.
