  • أي نقرة تحاول التفعيل → تومض لحظة → تعود للـ OFF خلال ~2 ثانية.
  • القيد no_config_wifi + WIFI_ON=0 لا يزالان نشطين (التحقق يبقى PASS).
  • بعد أي إقلاع: WifiBootReceiver يعيد تشغيل الخدمة ويعيد الإخماد — تبقى الحماية دائمة.

ملاحظة صريحة: لا يمكن للوكيل إعادة تلوين أيقونة SystemUI لتبدو رمادية مثل disabled في CSS — تلوين الأيقونة من واجهة البائع. لكن النتيجة العملية مطابقة تمامًا: الأيقونة لا تثبت على ON ولا تثبت على حالة فعّالة.

٨-٥) علة R1 — لماذا بقي WiFi معطّلًا بعد استعادة نقطة الحفظ؟ (الجذر + الإصلاح)

الظاهرة: أثناء التحقق من نقطة الحفظ R1_RESTORE_POINT، حذف الوكيل قيّد no_config_wifi من طبقة per-admin بنجاح، لكن WiFi ظل معطّلًا — لا WIFI_ON=1 يُعيده ولا svc wifi enable. نتيجة R1: PARTIAL.

السبب الجذري (دليل logcat):

$ adb shell "logcat -d | findstr -i setWifiEnabled"
09-16 17:48:26.662  WifiService: setWifiEnabled package=com.alp.agent uid=10196 enable=false isPrivileged=false

الخدمة الأمامية كانت ما زالت تُعيد إطفاء الراديو رغم مسح القيد! لأن شرط التنفيذ فيها كان:

Bundle cur = dpm.getUserRestrictions(admin);
if (cur.getBoolean(DISALLOW_CONFIG_WIFI)) { ensureWifiOff(); }   ← عبر المستخدم

على هذا البناء، dpm.getUserRestrictions(admin) تُرجع no_config_wifi = true حتى بعد مسح قيد الوكيل، لأن الـ Global Policies تحوي دخلاً افتراضيًا للضيف (Resolved Policy: null) يكفي لإبقاء القيمة true عند قراءة الـ Bundle. فخلافًا لما ظننت سابقًا، لم تكن الخدمة صامتة — كانت «مُصابّة» بنفس القراءة الكاذبة التي أصلحتها في المحرك.

الإصلاح — علم داخلي wifi_blocked بدلاً من قراءة القيود: يتمّ اتخاذ قرار التنفيذ من المصدر الحقيقي للحقيقة (طلبات الوكيل نفسها) بدلاً من قراءة سطرية يعبث بها بائع الـ Guest Defaults: 
applyRow(WIFI, BLOCK): putBoolean("wifi_blocked", true)   ← يُكتب فقط عند الحظر الفعلي
clearPolicy()         : putBoolean("wifi_blocked" , false) ← يُمسح فقط عند الاستعادة الكاملة
clearRestrictions()   : putBoolean("wifi_blocked", false) + dpm.setGlobalSetting(WIFI_ON=1)
AlpForegroundService / WifiBootReceiver: تنفيذ فقط إذا wifi_blocked == true

لماذا هو صحيح: الوكيل يعرف — من أي مسار (بثّ CLEAR أو تطبيق أو Rollback UI) — متى طلب النظام الحظر أو الاستعادة. هذه معلومات من الحزمة نفسها لا تتأثر بعيوب البائع في طبقة Global Policies.

اختبار الدورة الكاملة بعد الإصلاح — حظر ← استعادة (إثبات مباشر):

$ adb push e2e_apply.json /data/local/tmp/alp_envelope.json
$ adb shell am broadcast -n com.alp.agent/.CommandReceiver -a com.alp.agent.APPLY_POLICY --receiver-foreground
state.json: {"cmd_id":"E2E-APPLY-…","applied":["WIFI"]}
alp_stats.xml: wifi_blocked = true
$ adb shell cmd wifi status  →  Wifi is disabled   ✓  (wifi_on=0)

$ adb push e2e_clear.json /data/local/tmp/alp_rollback.json
$ adb shell am broadcast -n com.alp.agent/.CommandReceiver -a com.alp.agent.CLEAR_POLICY --receiver-foreground
alp_stats.xml: wifi_blocked = false               ✓
state.json: {"cmd_id":"CLEAR-…","applied":[]}
$ adb shell svc wifi enable
$ adb shell cmd wifi status  →  Wifi is enabled    ✓  (wifi_on=1)

الدروس المستفادة للتوثيق:

  • مسح قيد DpmManager.clearUserRestriction وحده لا يُغيّر قراءة getUserRestrictions() على LT-8110 (بقايا الـ Global defaults) — لا تعتمد عليه كشرط إيقاف.
  • قرار وزع التنفيذ يجب أن يكون حالة الحزمة لا حالة النظام: البوابة هنا SharedPreferences("alp_stats") / "wifi_blocked".
  • تنظيف alp_rollback.json حساس لـ cmd_id: إعادة إرسال نفس المعرف تُرفض عبر alreadyDone — يجب دائمًا توليد معرف جديد لكل طلب استعادة.
  • الاختبار الكامل أعلاه يُعاد في الجولة التحقق التالية: APPLY→true و CLEAR→false تُبقيان التحقق COMPLIANT وباستعادة فعلية للراديو (لا PARTIAL كاذبًا).
